# Accounts and Balances

- One account per user, created in the same transaction as the user

Registration currently does a single `INSERT INTO users`.
E3 adds a second insert, into `accounts`.
-- both have to succeed or fail together

## What breaks without the transaction

If the API crashes, the connection drops or if the second insert fails between two statements, you're left with a user who has no account.
That user can login, but every balance or transfer request then fails with a `500`.

Fixing this by creating the account lazily on first use introduces a race:
- two parallel first requests can create two accounts for the same user
-> A UNIQUE (user_id) constraint on `accounts` stops that

This is the *A* in *ACID* - atomicity:
- a transaction is all or nothing

The email taken path keeps working:
- `23505` on `users_email_unique` aborts the transaction
-> API still returns `409`

## Amounts: integer piconero

1 XMR-t = 10^12 piconero and every stored amount is a whole number of piconero

### Why not double?

Binary floating point cannot represent 0.1 exactly.
0.1 + 0.2 gives 0.30000000000000004.

### Integers are exact

Adding two `long`s is either exactly right or an overflow, and by default, C# wraps around silently to a negative number.
Only _checked_ arithmetic throws an `OverflowException`.

## Known limits

C#'s `long` and PG's `bigint`, the largest exact value can be 9.22 x 10^18 piconero, which is approximately 9.2 million in *XMR-t*.
JavaScript's `Number` is exact only up to 2^53, which is approximately 9.007 x 10^15 piconero, which is roughly 9,007 *XMR-t*.

That is why *JSON amounts are strings*. Without strings, a balance of 10,000 XMR-t would silently lose its last digits in the browser. The client parses `BigInt` and formats 12 decimals only for display.

## Balances are derived, never stored

There is no `balance` column. An account's balance is the sum of its ledger entries.

With a stored balance, there would be two sources of truths:
- the balance column
- the history

A bug or a partial update that changes one and not the other leaves them disagreeing.
If the balance is derived instead, it cannot disagree with its history, because _it is the history itself_.
The cost is `SUM` per read, which an index on `account_id` makes trivial at this scale.

### E4 link

The `accounts` row still matters in E4:
- before a transfer checks _"enough funds?"_, it locks the sender's row with `SELECT ... FOR UPDATE`, so two parallel transfers cannot both pass the check.

The row is the *lock*, so the ledger holds the *money*.

## Double-entry and the treasury

Every movement of money is a group of entries that *sums to zero*.
Money is never created inside a transfer, only moved.

Thus, the money first comes from:
- A single treasury system account (no user) that issues test funds through normal double-entry groups, for example [-100 for the treasury and +100 for Alice].
- So every amount in the system can be traced back to the treasury.
- The treasury is *the only account allowed to go negative*. Its balance is exactly minus all the money in circulation.
- For now, funds are issued only by a Development seed (demo users with starting balances), so there is no endpoint that issues money.

This results in two invariants which can be tested after any sequence of operation:

1. The sum of all ledger entries is `0`.
2. No non-system account has a negative balance.
- these also make for good attack tests

## Security side: whose account?

`GET /api/account` returns the balance of the account that belongs to the session's user, through `GetUserId()`. It never takes an account ID from the client, because if it did, `GET /api/accounts/2` would let Alice read Bob's balance.
This is known as an *IDOR* = Insecure Direct Object Reference.
