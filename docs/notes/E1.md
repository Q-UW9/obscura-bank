# E1: Registration and login (password storage)

## What it protects against

Assume the threat is that the database gets stolen.

An attacker gets a copy of the 'users' table, through SQL injection, a leaked backup or an insider. They can then guess passwords offline, because:

- there is no rate limit, no lockout and no logs,
- they have as many guesses as their hardware allows.

Hashing does not prevent theft - its job is to make every guess so expensive so that the stolen hashes are worth very little.

### Why not plaintext or encryption?

Plaintext means that every password is revealed immediately. People reuse passwords, so this exposes their email and other accounts as well.

Encryption implies that the kay has to be available to the application, thus whoever steals the database also gets the key. Encryption is _reversible_ and password retrieval is never needed, but password checking is.

What is actually needed is a one-way function, a _hash_, which is computationally infeasible to reverse. At login, the typed password is _hashed_ and the result is compared with the stored hash from the database.

### Why does a plain hash like SHA-256 fail?

SHA-256 is one-way, but it has two problems for passwords:

1. It is built to be fast.

A single modern GPU computes on the order of ten billion SHA-256 hashes per second. Every 8-letter lowercase password together is 2*10^11 candidates, whcih takes seconds or tens of seconds to try. Wordlists of leaked passwords are faster still.

2. It is deterministic.

The same password gives the same hash, so:
- attackers can precompute hashses of common passwords once (via rainbow tables) and look them up in every stolen database,
- users who share a password have identical hashes, so one cracked password reveals all of them.

## Proposed fixes

### Salt

A _salt_ is a random value, 16 bytes in our case, generated per user and stored next to the hash. The password is hashed together with the salt.

Thus, the same password gives a different hash for each user, so tables precomputed in advance are useless.
-> Every user has to be attacked separately. A million users means a million separate cracking jobs, not one.

The salt is not secret, it is stored in plain view, and it does not need to be hidden in order for it to do its job.
-> Guessing one user's passwords is not slower than before.

### Work factor

The has must be deliberately slow, with a tunable cost.

- For the server, one login costs a few tens of milliseconds, so it is not noticed.
- For the attacker, billions of guesses per second become perhaps tens per second per GPU.
- The cost can go up over time as hardware gets faster. That is why parameters are stored with each hash and why a _rehash_ is applied on login: a successful login is the only time a plaintext password is revealed, so it is the only time an old hash may be upgraded.

PBKDF2 and bcrypt work like this, but they only cost CPU time. A GPU has thousands of small cores, so it still runs thousands of slow guesses at once.

### Memory-hard Argon2id

Argon2 won the Password Hashing Competition in 2015 and is specified in RFC 9106. Every guess has to fill and repeatedly read a large block of memory:

- m = 19456 (19 MiB) per hash
-> A GPU's thousands of cores share a limited amount of memory, so only a fraction of them can work at once. Memory is expensive for attackers in a way raw compute is not.
- t = 2
-> two passes over that memory
- p = 1
-> one lane, meaning no parallelism inside a single hash


Argon2id combines two variants:
- Argon2i - which resists side-channel attacks, where an attacker learns something by watching memory access patterns
- Argon2d - which resists GPUs the best

These parameters are OWASP's recommended minimum.

The trade-off for this server is that every login costs 19 MiB and CPU time, so a flood of login requests may lead to a DoS attack. Rate limiting (B2) is one mitigation of this issue.

### PHC string

$argon2id$v=19$m=19456,t=2,p=1$<salt, base64>$<hash, base64>

This contains:
- the algorithm
- its version
- the parameters
- the salt
- the hash

One password_hast_text column is enough to store inside the database.

In order to verify it, the string must be parsed, then the typed password along with the salt is to be rehashed with _those_ parameters. Finally, compare.

If the stored m, t or p are lower than the current settings, the hash will need an upgrade on the next login.

### Constant-time comparison

A normal byte comparison stops at the first byte that differs, so the time it takes leaks how many leading bytes matched.
`CryptographicOperations.FixedTimeEquals` always compares every byte.

With salted hashes, this leak is hard to exploit, but the fix costs nothing and it is the standard habit for comparing secrets. This will also be reused for TOTP codes (B1) and tokens.

Registration may reveal whether an account already exists on the platform.
I suggested that all HTTP responses related to authentication which are not 200 OK should return a generic message. In order to mask the response time analysis, I remarked that padding response time could be a solution, such that the response whether an email exists (which is 1 ms as the database checks the existence of a row) and the password verification (which takes around 50 ms because of Argon2id's 19 MiB weight) return at around the same interval of time.
