# The problem

HTTP forgets you after every request, because HTTP is stateless. 
Each request stands alone.

After a successful login, curently a 204 inside the codebase, the server cannot tell that the next request _comes from Alice_. So login give the browser something it sends back with every request, and the server has to be able to recognize it.
This is called a *session*.

## Two models

Server-side vs. stateless

In a server-side session, *the cookie holds* a long random token, meaningless on its own, *the server holds* a row, a token identifying the user, which is created and can expire. *When checking a request*, the token is looked up inside the database. *On logout and revocation*, the row is deleted and it is immediately invalid everywhere. *The cost* is one database lookup per request.

Using a stateless token, _such as JWT or ASP.NET's default encrypted cookie_, the login itself (user ID, role, expiry) is signed or encrypted. *The server thus holds* nothing and when *checking a request* it verifies the signature or decrypts the cookie, with no database. *Logout and revocation* are impossible before expiry, because a copied cookie stays valid until it runs out, unless a denylist is kept on the server, which makes it stateful again. *The cost* is none, which is why it is popular at large scale.

For a bank, revocation decides it. 
_Log out_ has to mean the session is over, not just that the cookie disappeared from _this.browser_.
This is why my stack decision is *server-side sessions*.

# The token

- unguessable
- never derived from anything

The token comes from `RandomNumberGenerator`, the same generator as the salts: 32 bytes = 256 bits.
Guessing one is hopeless, even across millions of active sessions.
! Never use sequential IDs (session=42) or anything derived from the user ID or the time. !

## Cookie flags

- each flag stops a specific attack

*The flag* `HttpOnly` has *the effect* that JavaScript cannot read the cookie through `document.cookie`. This *stops the XSS stealing the session attack*. Injected script cannot send the token to an attacker, though it can still act as the user while the page is open.

*The flag* `Secure` *means* that the browser sends the cookie only over HTTPS. This *stops* sniffing, for example on public Wi-Fi, such that the token never travels in plaintext.

*The flag* `SameSite=Lax` or `Strict` has *the effect* that the cookie is not sent on requests that another site triggers. The *stopped attack* is most CSRF, where `evil.com` submits a form to your bank. This is not complete protection without CSRF tokens!

*The flag* `__Host-` name prefix *means* that the browser only accepts the cookie with `Secure`, `Path=/` and no `Domain`. This *stops* cookie injection from subdomains, such that a compromised `blog.example.com` cannot plant its own session cookie for `example.com`.

Finally, *the flag* no `Max-Age`, or a short one, has *the effect* that the cookie ends with the browser session. This *prevents* leftover sessions on shared computers.

# Expiry enforcement

A cookie's expiry date is only a *request to the browser*, and an attacker with a copied token simply ignores it, so the server stores the expiry in the session row and checks it on *every* request. 
There are usually two limits:

- Idle timeout = expires after _N_ minutes without activity;
each request pushes it forward, also known as _sliding_.
- Absolute timeout = ends at the latest after _N_ hours, however active the session is. That limits the damage from a stolen token.

## Session fixation

Attack scenario:

1. Attacker gets a valid session token, for example by opening the login page themselves.
2. They plant it in the victim's browser, for example through a subdomain (`__Host-` case) or a vulnerable page.
3. The victim logs in.
4. If the server keeps the same token and just attaches "Alice" to it, the attacker's copy is now logged in as _Alice_.

The fix is that every login creates a brand-new token, and the old one, if there was one, is deleted.
With purely server-side sessions there is a second line of defence:
the server never accepts a token that it did not create itself, so an unknown token simply does not match any row.

## Logout has to happen on the server

Deleting the cookie only removes the token from *this.browser*.
A stolen copy would keep working.

Proper logout deletes the row and then removes the cookie.

# Authentication vs. authorization

The store can tell which user a token belongs to.
What is still missing is the link to ASP.NET Core: reading the cookie on *every* request and turning it into a logged-in user, so that an endpoint can be protected with a single `.RequireAuthorization()`.

ASP.NET Core splits this into two questions, asked one after the other:

1. `UseAuthorization` asks _"Who is this?"_. My handler reads the cookie, hashes it, looks it up in the store and builds the current user or leaves the request anonymous.
2. `UseAuthorization` also asks _"May they do this?"_. It decides per endpoint, using the user from step 1.
3. Only then does the endpoint run and it sees the user.

## Anonymous is not an error

*Authentication* only establishes the identity. A request without a cookie, or with an unknown or expired one, is not rejected there, it is simply *anonymous*.
That is necessary, because `/api/health/db` and `/api/auth/login` have to keep working without a cookie. Nobody can log in if logging in requires being logged in.

The rejection happens later in *authorization* and only on endpoints that ask for it.

## 401 vs. 403

- 401 Unathorized = The endpoint requires login and the request is anon
- 403 Forbidden = Logged in but not allowed - usually wrong role

The names are historical, because 401 really means *unauthenticated*.
! The API never redirects to a login page. A JSON API answers with the status code and the React client decides what to show. !

## Claims principal

A `ClaimsPrincipal` is .NET's representation of _the current user_: a set of *claims*, each a type and a value, such as *user ID* = 1 and *role* = user.

My handler only has to produce one and everything after it works without knowing anything about sessions or cookies.

## What breaks without it

Without the handler, every endpoint would have to read the cookie, hash it and query the store itself.
*One forgotten check* would mean an endpoint to anyone. With the handler, the check lives in one place and protection of an endpoint is one line that is easy to spot in a review.
